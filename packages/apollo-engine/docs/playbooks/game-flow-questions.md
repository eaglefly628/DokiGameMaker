# 游戏生产流程 = 任务问题清单（每步答得出 YES 才算过）

> owner 2026-07-25：「优化以后游戏的流程，总结成以任务的问题。」
> 病根（Lead 诊断·owner 2026-07-25 校正）：真正卡住的**不是「好不好玩」，是最基本的逻辑闭环**——
> 开始→操作→分出胜负/推进→重开，这条环常常根本跑不通（空按钮 / 死路 / 胜负永不触发 / 虚胖数据）。
> 为什么数据驱动特别容易断环：环被摊在 N 组件 + M 能力 + **字符串对名的信号/id 引用**里，模型抓不住整张图，
> 边就悄悄没接上。现有门只测**引擎契约**（load 得下？`validate-references` 引用不悬空？tsc 绿？）和**不崩**
> （`manifest-check` 空跑 2 tick）——**没有一道门证明「这条环真能从头跑到尾」**。而这件事**可被机器证明**
> （不像好不好玩要人判）：`scripts/acceptance-run.mjs` 已能让 GD 写纯数据剧本、驱动**真引擎逐步对账**。
> 药方：把「闭环跑通」钉成**第一道·强制·机器证**的门（下面 T2）；好不好玩（T4/T7）是它之后的事。

## 用法
- 一个会话只领一个任务；开工先 `node scripts/game-pipeline.mjs board <slug>` 看当前非绿任务。
- 过关 = ①机器门（脚本·客观**下限**）+ ②**任务问题答 YES**（人门·真玩真看·note 写证据）。缺任一 = 停，不许往前。
- **报告纪律**：只许说「做到 T-N·问题已答 YES（证据 …）」；**禁**「门全绿=做完了」（口头完成无效·呼应 game-production §红线）。

## 相比旧八阶段变了什么（这就是「优化」）
1. **加 T2 闭环竖切 + 机器证明**：不再横铺堆量；先把**一条最小循环跑通**，用**已有的验收剧本 conformance**（真引擎逐步对账）**机器证明它闭合**，再往外长。这是**下限不是好不好玩**——闭环跑通是「好玩」的前提，先保证它。
2. **每个任务钉一个「答得出才算过」的问题**：能机器答的（闭环/引用/审计）机器答，答不了的（手感/观感）人答、note 留证据。
3. **T4 手感单列**：手感是「游戏 vs demo」的分水岭，旧流程散在 UI/品质里没人负责——现在是独立一道问题（但排在 T2/T3 闭环之后）。
4. **报告口径收紧**：绿门只代表「没坏」；「做完了」必须附对应任务问题的 YES + 证据。
